# 验证速度档位与耗时

启动器负责让原生菜单把所选档位传入请求。请求档位、上游实际采用的档位和任务耗时需要分别核对。

## 先核对档位

在同一模型、同一 Key 和同一推理强度下依次选择 Standard、Fast、Standard，发送三条新请求。中转的服务档位筛选、上游请求日志或返回的 `service_tier` 应能说明各次请求的实际处理档位。

如果只能看到请求体里的 `priority` 或 `fast`，可以确认客户端发送了 Fast 意图；还需要上游响应或服务端记录，才能确认实际上游处理档位。中转可能筛掉该字段，上游也可能拒绝或回退。

## 再比较耗时

使用固定题目，保持模型、推理强度、上下文长度、工具和输出要求一致。按 Standard／Fast 交错顺序各执行多轮，避免把时段负载差异当成档位差异。测试会产生真实用量，按所用中转和上游费率计费。

| 指标 | 含义 |
| --- | --- |
| 首字时间 | 发出请求到收到首个内容片段；包含网络、排队及部分推理时间 |
| 总耗时 | 发出请求到响应结束；会受到回答长度和工具执行的影响 |
| 输出 token 数 | 用于识别“回答更短所以更快”等差异 |
| 输出速率 | 能取得生成起止时间时，以输出 token 数除以生成时长；不要把总耗时倒数当成纯生成速率 |
| 实际服务档位 | 从上游响应或服务端记录读取，检查是否回退 |

记录每档的中位数并保留各轮数据，避免仅凭某一轮结论。长任务还包含工具调用、文件读写和外部命令，生成加速对整段任务的影响可能不明显。

## 官方说明

[Fast mode 文档](https://developers.openai.com/api/docs/guides/fast-mode)说明 `fast` 与旧值 `priority` 的兼容关系，以及部分流量可能回退到默认档位。服务档位接受与否不由启动器决定。

[Ultrafast mode 文档](https://developers.openai.com/api/docs/guides/ultrafast-mode)说明独立的 `ultrafast` 档位，并建议用 WebSocket 复用连接降低网络开销。客户端和中转是否实际支持该值，需要单独验证。
