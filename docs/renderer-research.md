## 原因和适配范围

当前客户端使用 `serviceTierAccess` 对速度功能作统一判断。界面入口和发送请求使用两个独立路径：

| 入口 | 当前行为 | 本工具的处理 |
| --- | --- | --- |
| 界面速度权限 hook | 仅为 ChatGPT、PAT、Bedrock 登录读取速度权限；API Key 和自定义供应商返回 `null` | 对 `apikey` 和自定义供应商使用的空认证方式返回 `{ fast: true, ultrafast: false }`；等待认证时仍返回不可用 |
| 独立请求权限 helper | API Key 和空认证方式直接返回 `null`；编辑、恢复等流程也会使用此入口 | 对上述两种接入返回相同的 Fast 能力，继续使用原有请求档位解析 |

ChatGPT、PAT、Bedrock 的权限查询、`fast_mode` / `ultrafast_mode` 限制和错误处理保持原有行为。不识别的认证方式继续返回不可用。

界面权限 hook 原先只按「是否为托管登录」缓存计算结果。适配后，同一个缓存槽位改为记录认证方式，保证 API Key 与其他非托管认证方式互相切换时重新计算，避免沿用上一种认证方式的速度权限。

本版没有强制显示独立 UI，也没有改写请求模型名称。原生菜单仍要求所选模型的 `serviceTiers` 包含可用档位。选择 Fast 后沿用客户端已有的 `priority` 档位；Standard 沿用客户端的标准请求行为。

这两处适配仅解除 API Key 接入的客户端限制。服务端仍需要支持所选模型、接受并透传服务档位；上游的认证、计费和排队策略仍由服务端决定。

## 模型能力与 Ultrafast

对该客户端附带的 Codex 执行只读命令 `debug models --bundled`，确认 `gpt-6.1-sol`、`gpt-6-astra`、`gpt-6.1-terra`、`gpt-6-sol`、`gpt-6-luna`、`gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna`、`gpt-5.5` 的内置模型条目已有 `priority` / Fast 元数据。该命令只用于读取模型目录，没有发起模型请求。

这些内置条目未声明 Ultrafast。本版对 API Key 分支只开放 Fast，不添加 Ultrafast、额外模型或模型别名，也不覆盖用户现有模型目录。自定义模型没有相应速度元数据时，菜单可能仍不显示；需要另行核实该模型能力。

## 已有聊天和全局默认值

客户端原生逻辑区分全局默认档位、聊天档位和正在保存的菜单选择。本版保留这个逻辑：正在选择的档位优先；已有聊天明确保存的档位可覆盖全局默认；新聊天或未设置档位的聊天使用默认值。

因此，在设置页修改全局默认值，不意味着所有已有聊天的速度都会被覆盖。检查已有聊天时，应在该聊天的速度菜单中确认选中的档位，再核对新请求。启动器不会为追求全局一致而删除聊天自己的明确选择。

## 自动化检查与验收边界

`node --test test/speed-patches.test.mjs` 使用手写最小夹具执行补丁后的函数。测试覆盖 API Key、空认证、自定义未知认证、认证方式切换后的 React 缓存、认证等待、ChatGPT / PAT / Bedrock 权限、Standard → Fast → Standard、独立发送路径、已有聊天选择保留、重复应用和不明确签名拒绝。

这些测试和归档语法检查确认了结构匹配与函数行为。它们不能替代真实应用窗口中的菜单操作，也不能证明中转站或上游已经处理 Fast。完整验收需要隔离用户配置下的桌面 UI 操作，以及新请求的 `service_tier` / 服务端记录核对。实际联调状态以交付包的验证记录为准。

macOS 尚未取得对应客户端归档并完成真机验证。若其前端采用同样结构，可复用本模块的匹配逻辑；签名不一致时应停止，不能假定 Windows 构建结论适用于 macOS。
