# 开源与发布

Codex Speed Launcher 是采用 MIT 许可证的独立工具，可与 Sub2API 等兼容的 Responses 中转配合使用。当前源码没有包含 Sub2API 源码；中转自身的许可证和部署方式独立管理。

## 公开仓库内容

公开启动器源码、自动检查、构建脚本、使用文档、MIT 许可证和第三方声明。沿用代码的版权及许可证继续保留。仓库不应包含官方 Codex 程序、用户配置、真实地址与 Key、会话、数据库、缓存或本机测试报告。

从源码包新建独立仓库；不要把包含其他项目及历史数据的父工作区直接公开。源码包附带 `.gitignore`、检查工作流和草稿发布工作流。

## 下载形式

| 形式 | 适合用途 | 当前状态 |
| --- | --- | --- |
| Windows 单文件 EXE | 免安装启动，减少解压后文件管理 | 提供命令行窗口，便于显示检查和运行状态 |
| Windows 便携 ZIP | 保留源码、文档、运行时，便于检查与排错 | 保留为备用下载 |
| macOS `.app` 与 DMG | 图形界面和拖动安装 | 后续方向，需要 Mac 真机、签名和公证验收 |
| macOS 脚本 ZIP | 小范围试用与兼容性研究 | 当前为实验支持 |
| 安装器与托盘应用 | 桌面快捷方式、常驻状态和更新管理 | 后续根据使用反馈决定 |
| 源码 ZIP／Git 仓库 | 审查、修改和自行构建 | 与可执行文件同时提供 |

ZIP 是发布附件的容器；图形界面、安装流程和托盘属于独立功能。当前 EXE 仍是控制台启动器。Windows 安装器不会自动使其成为图形应用。

## 发布步骤

1. 在独立仓库检查版本、许可证、第三方声明和待发布文件，运行自动检查及平台验收。
2. 运行构建脚本，核对文件清单和 SHA-256，使用解压后的包或最终 EXE 再检查。
3. 推送版本标签，例如 `v0.1.1`。标签必须与 `package.json` 一致。
4. `Build release draft` 工作流生成可下载文件并创建草稿 Release；检查附件、兼容版本和未验证范围后，再在 GitHub 发布草稿。

手动运行工作流只上传构建附件，不创建公开 Release。工作流的逻辑检查可以在未安装 Codex 的托管运行器上执行，不能代替实际桌面菜单和请求验收。

Windows EXE 当前没有项目发布者的代码签名。签名需要发布者自己的证书或签名服务；打包过程不借用 Node.js 原有签名宣称项目已签名。macOS 正式版同样需要独立签名、公证及真机验收。

## 后续维护

每次 Codex 更新重新检查结构签名与菜单请求；不匹配时停止启动。发布说明写明具体客户端版本和验证方式。

后续可增加图形化兼容性检查、启动状态、桌面快捷方式和速度诊断。自动更新、托盘常驻及安装器应有明确用途后再引入，避免首版承担额外维护范围。
